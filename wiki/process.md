# 本次建立與教學簡報工作流程

## 先討論，再生成：需求決策

**討論題目：** 如何讓第一次使用東京旅遊 Wiki 的人，理解 Wiki 如何把零散餐飲資料整理成可檢索、可檢查的知識，再用於教學型簡報？

**決策：** 受眾設定為不熟悉 LLM Wiki 的初學者；簡報以「東京美食 Wiki 如何支援選擇」為案例，先解釋原始資料、Wiki 條目與檢索的差異，再示範按料理類型及地區取回內容，最後展示來源檢查與實際使用前的資訊確認。避免把餐廳推薦包裝成即時或權威建議。

**資料欄位：** 店名／地區／料理類型／用餐情境／條目摘要／來源 ID／來源狀態／易變資訊提醒。這讓查詢結果有一致結構，也能在生成前辨識哪些敘述缺乏來源。

## Loop / graph 設計

```text
討論受眾與教學目標
        ↓
盤點附件、索引、raw/inbox、來源 ID
        ↓
選取五篇餐飲條目作為 ingest 語料
        ↓
格式解析與正規化 ──失敗──→ 修復 Markdown／欄位後重跑解析
        ↓ 成功
建立來源登錄與可信度標籤
        ↓
Wiki 查詢（地區／料理／用餐情境）
        ↓
抽取重點＋逐項連回來源（claim-to-source）
        ↓
內容閘門：來源可追溯？易變資訊有標記？初學者看得懂？
   ├─ 不通過 → 回到 Wiki 查詢或補來源，重寫受影響段落
   └─ 通過
        ↓
產生 HTML 簡報頁面
        ↓
版面／完整性／事實一致性檢查
   ├─ 溢位或內容錯置 → 回到該頁重寫並重檢
   └─ 通過 → 發佈簡報與提交文件
```

## 哪些步驟會重複？

格式解析遇到非法跳脫字元時，修復後重跑解析。若 Wiki 查詢無法提供足夠且有來源支援的內容，回到檢索或補充來源。每個簡報頁面的內容都必須經過「主張—來源」核對；若來源不足，縮小主張或加上限制。Slides 渲染如發現高度超出、層級不清或文字過密，則只修正受影響頁面並重新檢查。

## 哪些地方必須檢查？

- **Ingest 前：** 原始資料是否存在、來源 ID 能否對應、檔案格式能否解析。
- **整理後：** 條目是否保留來源與不確定性，時間敏感資訊是否加註待查。
- **生成前：** 每個要教的重點是否有 Wiki 條目或外部來源支持，內容是否符合初學者程度。
- **生成後：** 簡報頁是否完整、HTML 是否有效、文字是否超出版面、引用是否放在相關主張附近。

## 一次實際執行與檢查紀錄

- 輸入：使用者提供的 `travel-planner-wiki.zip`。
- 盤點：找到五篇餐飲頁、五篇資訊稀少的景點頁、一篇行程頁；`raw/inbox/`、`index.md`、`log.md`、`index.html` 原本為空或沒有有效內容。
- 發現：餐飲頁的 Markdown 標題、清單與 front matter 含多餘反斜線或 HTML 空格實體；原有來源 ID 找不到對應原始資料。
- 格式修復：移除非語義性的跳脫符號，保留內容，並建立可讀索引與來源登錄。五篇頁面都保留為五筆 ingest 資料單位。
- 來源檢查：查閱 SAVOR JAPAN 的文字燒概念文章，只以它支持文字燒的一般介紹；不將它擴張為對「もへじ」店家細節的背書。
- 生成前閘門：簡報只使用 Wiki 可支持的類型、地區與條目組織方式；價格、營業時間及店家現況不作為已核實建議。
- 輸出檢查：簡報頁面逐頁撰寫並由 Slides 交付閘門確認沒有待完成頁；Word/PDF 另行檢查標題層級、文字抽取與頁面渲染。

## 反思與 workflow 調整

**最常出錯的節點：** Ingest／正規化。這次原始資料層缺失，來源 ID 無法追溯，且 Markdown 跳脫字元使文件表面上存在、實際上不易閱讀。它也會連帶造成錯誤引用或把舊資料當成即時資訊。

**把檢查往前移：** 將來源檢查前移到 ingest 入口，並在內容整理前檢查「原始檔存在、來源 ID 對得上、格式解析成功」三項。缺一時可以繼續整理教學範例，但必須標記為「附件既有整理／未核實」，不能直接寫入已驗證事實。

**是否修改 graph：** 有。新增 ingest gate 與 claim-to-source 閘門，並將易變資訊判斷放在簡報生成之前。理由是越早發現來源缺失，修正成本越低，也可避免錯誤沿著摘要、教學大綱一路複製到成品。
